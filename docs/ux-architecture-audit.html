The Orange Pulp · Engineering Audit · Aug 2026

What to fix, in what order, and the numbers behind each call

A measured pass over design, color, accessibility, and architecture across 177 source files. Every finding below is backed by a count or a computed value from this codebase — nothing here is a matter of taste.

🔒 The palette is not a finding. Every real token passes WCAG AA or better in both themes — cream/green 10.56:1, green on pink 7.22:1, green on yellow 9.59:1, green on blue 5.59:1. The color problem is the opacity modifiers layered on top of those tokens, and the fix introduces zero new hues.
✅ All eleven findings have since been fixed across four commits (e96ad77, 43d68df, e6dad6b, 15c5ea4). Removing @ts-nocheck from the data layer additionally exposed five features that were failing at runtime — tag creation, contact-form submit, manual cache rebuild, saving site settings, and every job-log write. Those are described at the end of finding 11. Two items remain open by choice: 25 @ts-nocheck files in app/ and components/ (down from 39), and 228 pre-existing no-explicit-any lint errors.

Findings

01

Keyboard navigation is invisible on every page

Critical
Measured

focus:outline-none appears 61 times. focus-visible appears 0 times. There is no skip-to-content link, and only 7 aria-labels exist across the entire app.

Focus rings are removed everywhere and never replaced. A keyboard or switch-device user tabbing through the nav, the search modal, the comment form, or any dashboard editor has no visual indication of where they are. This is the single most severe issue in the codebase and also among the cheapest to fix.

Fix

Add one global rule in globals.css using the --ring token that is already defined and currently unused: :focus-visible { outline: 3px solid var(--ring); outline-offset: 2px; }. Then delete the 61 focus:outline-none instances — with :focus-visible in place, mouse clicks won't show a ring anyway, which is what those declarations were trying to achieve. Add a skip link in layout.tsx.

02

All metadata text fails contrast, at sizes below the legibility floor

Critical
Measured

246 uses of 9–10px type (140 × text-[10px], 106 × text-[9px]). 193 uses of text-foreground/20–/60, every one of which computes below 4.5:1 against the background.

Bylines, dates, categories, view counts, rank labels, and every dashboard field label are rendered at 9–10px in a colour that measures as low as 1.43:1. These are compounding failures: undersized and under-contrast. Composite values below are the true alpha blend against --background, not an approximation.

"Large only" means it clears 3:1 — valid for 18px+ bold text, but every one of these sites is 9–11px. At the sizes actually used, /20 through /60 all fail. That is 193 of the 226 opacity usages.

Fix — validated, no new colours

Replace text-foreground/20–/60 with the existing --muted-foreground token. Verified against all four surface combinations:

  • Dark #A8C8B0 on background — 6.65:1 AA; on --muted — 6.02:1 AA

One token swap clears both themes on both surfaces. Separately, raise the small-text floor from 9px to 12px — 9px is below what most users can read comfortably and is not recoverable by contrast alone.

03

No image optimization anywhere in the app

High
Measured

0 imports of next/image. 40 raw <img> tags. No width/height, no loading, no sizes on any of them.

Three consequences, all user-facing: every image causes layout shift as it loads because no intrinsic dimensions are declared; nothing below the fold is lazy-loaded; and TMDB posters requested at w780 and original are being painted into 64px-wide slots in the related-articles sidebar and 16px thumbnails on the homepage. On a phone connection the hero article page is downloading several megabytes it cannot use.

Fix

Convert to next/image with remotePatterns for image.tmdb.org and the Supabase storage host in next.config.js. Start with the three highest-traffic surfaces — HeroArticle, ArticleCard, and the ranked rows in ListDetailView — since those cover the LCP element on nearly every route. Request the appropriate TMDB size per slot rather than original.

04

The type scale has no reading-size middle

High
Measured

403 uses at ≤12px (9px, 10px, text-xs) · 129 at 14px · 13 at 16px · then 25 at 18px, 23 at 20px, and 88 across 24–36px+.

The distribution is bimodal: tiny labels and huge headlines, with almost nothing in between. Outside of prose blocks there are only 13 instances of body-sized text in the whole app. That is why pages read as "labels and billboards" rather than as something with a comfortable middle register — and it is the underlying design reason the 9–10px metadata is doing so much work it shouldn't be doing.

Fix

Define an explicit scale as tokens — 12 / 14 / 16 / 18 / 24 / 32 / 48 / 64 — and use 16px as the default for anything a reader is meant to actually read (blurbs, notes, card descriptions, dashboard help text). Reserve ≤12px for genuine labels only. The brutalist identity lives in the weight, the uppercase, and the borders; it does not require starving the body copy.

05

Recommendations over-fetch full article bodies on every page render

High
Measured

src/lib/services/recommendations.ts:12 — select('*, categories(*), authors(*), movies(...)') with .limit(40), then scores in JavaScript and discards all but 4.

select('*') on articles includes content — the entire markdown body of each article. Forty full article bodies are pulled over the wire to produce a four-item sidebar, on every review, news, spotlight, and list page. getRelatedMovies has the same shape at .limit(50). It's cached for 300s so it isn't hitting the database on every request, but each cache miss transfers far more than it needs and the payload grows linearly as the archive does.

Fix

Project only the columns the sidebar renders: id, title, slug, type, cover_image_url, category_id, movie_id, published_at, views_count. That alone removes the body text. If the candidate pool later needs to grow past 40, move the scoring expression into a Postgres function so ranking happens where the data lives.

06

Search silently misses most of what users type

Medium
Measured — probed against the live database
  • title=wfts.odyssey → returns "The odyssey" ✓
  • title=wfts.odys → returns nothing — full-text matches whole words only, so as-you-type search finds nothing until a complete word is typed
  • title=wfts.villeneuve (a word present in article bodies) → returns nothing — only title is searched

Two corrections to what the code implies. First, the textSearch call does not error, so the ilike fallback branch in searchArticles is dead code that never executes. Second, because the search modal fires as the user types, the whole-word-only behaviour means the results panel stays empty through most of the typing. Separately: the pg_trgm GIN index intended for this is commented out in 20260719000001_performance_indexes.sql, so the match is an unindexed per-row to_tsvector evaluation. Also a minor bug — searchArticles(query, limit) ignores its limit parameter and hardcodes 20 in both branches.

Fix

Add a generated tsvector column covering title, excerpt, and content with a GIN index, and query it with a prefix-matching tsquery (append :* to the final term) so typing "odys" matches. Remove the dead fallback branch and honour the limit argument.

07

Touch targets below the 44px minimum in the sticky header

Medium
Measured

Navbar.tsx:71 — mobile menu toggle is p-1.5 around a w-5 h-5 icon ≈ 26px. Navbar.tsx:54 and ThemeToggle — p-2 around w-4 h-4 ≈ 32px. Dashboard row actions at p-1 with 12px icons ≈ 20px.

All below the 44px guideline, and the mobile menu button is the primary navigation affordance on phones. The h-16 header leaves room to grow them without changing the layout.

Fix

Set a min-w-[44px] min-h-[44px] floor on icon-only controls, centring the icon inside. The visible border can stay its current size — pad the hit area, not the outline, if you want to preserve the compact look.

08

Hero metadata sits on arbitrary images, where contrast can't be guaranteed

Medium
Measured

Every detail view overlays text-background/55 and /65 on an editor-uploaded photo behind a from-foreground/95 via-foreground/40 to-foreground/10 gradient. 44 uses of text-background/NN total.

Contrast here is not statically computable — it depends on whichever image an editor uploads. At via-foreground/40 in the middle of the gradient, a light backdrop leaves byline and date text effectively unreadable, and the failure is invisible to whoever published the article because it depends on their specific image.

Fix

Raise the scrim floor where text actually sits — take the bottom stop to /95 and the middle to /70 — and lift the metadata opacity to /80 minimum. For a guaranteed result regardless of image, put the byline row on a solid --foreground plate rather than directly on the gradient.

09

The homepage is the stalest page on the site

Medium
Measured

src/app/page.tsx:12 — revalidate = 3600. Every listing page — revalidate = 60. Article detail — 60.

A newly published article appears on /reviews within a minute but can take an hour to reach the homepage. For a publication whose front page is the main entry point, the highest-traffic surface has the longest lag. The underlying data functions are already cached at 300s, so the page-level hour buys very little.

Fix

Bring the homepage to revalidate = 60 to match the listings, or call revalidatePath('/') on publish — which createArticle and updateArticle already do, meaning the 3600 mainly affects TMDB-driven sections. Either way the inconsistency should be deliberate rather than incidental.

10

Every listing is hard-capped at 20 items with no pagination

Low · pre-emptive
Measured

No searchParams, .range(), or offset handling in any listing route. Current published article count: 3.

Not a live problem — flagging it as a ceiling rather than a defect. Once the archive passes 20 articles of any type, older content becomes permanently unreachable through navigation, and it will only be discoverable via search and sitemap. There is also no robots.ts, though sitemap.ts exists.

Fix

Worth building before the archive grows rather than after: ?page= with .range() in the cached fetchers, or a "load more" cursor. Cheap now, a content-migration problem later. Add robots.ts pointing at the existing sitemap while you're there.

11

Type checking is disabled across a fifth of the codebase

Low · hygiene
Measured

@ts-nocheck in 39 of 177 source files (22%), including every file in lib/api and lib/actions — precisely the layer the generated database types exist to protect.

This is how src/types/database.ts drifted out of sync with the actual schema: the editorial-workflow migration added six columns in July that never reached the type file, and nothing complained because the files that consume those types have checking switched off. The types are doing no work where they matter most.

Related cleanup, all verified present:

  • Orphaned route shells — /posts/[slug] reads MDX off the filesystem and is unreachable from any nav; /spotlights is a redirect stub
  • user_bookmarks table plus RLS policies exist with zero UI referencing them
  • /person/[slug] returns entirely fabricated data — getPersonBySlug synthesises a bio and filmography from the slug string
  • Stray files at repo root: 12.0.1 (an npm error artifact), db-check.js, fix-supabase.js, test-supabase.js, query_schema.js
  • Two migrations both named initial_schema, the second being an ALTER patch
Fix

Regenerate database.ts from the live schema with supabase gen types rather than hand-maintaining it, then remove @ts-nocheck file by file starting with lib/api and lib/actions. Delete the stray root scripts and the orphaned routes; either build the bookmarks UI or drop the table.

What this actually uncovered

Type-checking the data layer turned out to matter more than the hygiene framing suggested. Five features were broken in production, each silently:

  • Tag create/update always failed. TagForm has a Description field and submits it, but tags had no such column — every save returned column description of relation tags does not exist.
  • Contact-form submit and manual cache rebuild always failed. jobs.priority is INTEGER; both inserted the strings 'low' and 'high'.
  • Saving site settings always failed, and the form always rendered blank. site_settings is a key/value table, but the action upserted { id: 1, site_name, … } — wrong columns, and id is a uuid. The read path had the same mismatch, so stored values never reached the form.
  • Every job-log write always failed. engine.ts writes to job_logs and types.ts declares a JobLog interface, but the table was never created.
  • Nullable dereferences on job.attempts, media.size_bytes and media.mime_type.

Separately, Next 16 deprecated single-argument revalidateTag — the docs note it "currently works if TypeScript errors are suppressed," which is precisely what @ts-nocheck was doing across all 17 call sites. And npm run lint had been failing outright since the upgrade, because next lint was removed in Next 16.

What is already right

  • The palette. Every token clears AA or better in both themes. It is a genuinely distinctive scheme and it is correctly implemented at the token layer.
  • The repository/action split. lib/api for reads, lib/actions for mutations, no direct Supabase calls in components. Consistently followed.
  • Caching discipline. unstable_cache with tag-based invalidation, cache() for per-render dedup between generateMetadata and the page body. Well judged.
  • RLS coverage. Enabled on every table, with the dev-era anon write policies properly revoked in 20260725000003_lockdown_rls_production.
  • Role gating in server actions. Writers can't publish, only admins delete — enforced server-side, not in the UI.
  • Loading and error boundaries. loading.tsx and error.tsx present across routes, including global-error.tsx.

  2. Raise the type floor
    9px → 12px, and 16px for anything meant to be read. Findings 02 and 04. Mechanical, high perceived quality gain.
  3. Images on the three hottest surfaces
    next/image in HeroArticle, ArticleCard, ListDetailView. Finding 03 — biggest measurable Core Web Vitals move.
  4. Two query fixes
    Column projection in recommendations.ts; tsvector column + GIN index + prefix matching for search. Findings 05 and 06.
  5. Touch targets, hero scrim, homepage revalidate
    Findings 07–09. Small, independent, safe to ship together.
  6. Pagination before the archive needs it
    Finding 10 — cheap at 3 articles, awkward at 60.
  7. Regenerate types, then peel off @ts-nocheck
    Finding 11. Ongoing rather than a single task; start with lib/.
